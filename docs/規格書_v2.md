# PCI 餐廳回饋系統 — 系統規格書 v2

> v2 修訂重點：管理者登入機制、代碼化欄位設計、圖片壓縮規格、防重複提交、多語系架構、每日未處理通知
> 修訂日期：2026-08-18

---

## 一、系統概述

本系統供 PCI adidas 工廠員工在餐廳用餐時回報問題與建議，管理者透過專用介面進行案件追蹤與回覆，所有資料自動彙整至 Google Sheet。

| 項目 | 內容 |
|---|---|
| 系統名稱 | PCI 餐廳回饋系統（PCI Cafeteria Feedback System） |
| 員工人數 | 約 8,000 人 |
| 預估回報量 | 每月 50 筆以內 |
| 管理者 | 初期 5 位，可自行擴增 |
| 介面語言 | 印尼文 / 中文（可切換） |
| 存取方式 | 員工手機掃 QR Code、管理者電腦瀏覽器 |
| 技術架構 | GitHub Pages（前端）+ Google Apps Script（後端）+ Google Sheet / Drive（資料層） |
| 費用 | 零成本 |
| 系統時區 | **Asia/Jakarta（WIB）— Apps Script 專案建立後第一件事就是設定** |

### 容量評估（依上述規模推算）

| 項目 | 預估 | 上限 | 餘裕 |
|---|---|---|---|
| 資料列數 | 600 列/年 | 500 萬列 | 極大 |
| 圖片儲存 | 約 360 MB/年（壓縮後） | 15 GB | 約 40 年 |
| 案件流水號 | 50 筆/月 | 999 筆/月 | 充足 |
| 月報 Email | 5 封/月 | 100 收件者/日 | 充足 |

**結論：規模完全在免費額度內，不需要為擴充性做額外設計。**

## 二、系統架構

```
        員工（手機，匿名存取）              管理者（電腦，需登入）
               |                                    |
               ▼                                    ▼
    ┌──────────────────── GitHub Pages 前端 ─────────────────────┐
    │  [語言選擇] [回報表單] [案件查詢]  │  [登入] [案件管理] [帳號管理] │
    └───────────────────────────┬───────────────────────────────┘
                                │  HTTPS / JSON
                                │  （管理端請求需附帶 token）
                                ▼
                    ┌───────────────────────┐
                    │  Google Apps Script   │
                    │  ─ 路由 / 驗證 / 鎖    │
                    └───────┬───────────────┘
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
      ┌──────────────┐            ┌──────────────┐
      │ Google Sheet │            │ Google Drive │
      │  8 個分頁     │            │  圖片資料夾   │
      └──────────────┘            └──────────────┘
```

### 資料流向

**員工提交：**
1. 前端驗證工號 → Apps Script 比對名冊 → 回傳姓名
2. 前端**壓縮圖片**（長邊 1600px / JPEG 0.8）→ 轉 Base64
3. 前端產生 `client_submit_id`（防重複）→ 打包資料送出
4. Apps Script 取得 ScriptLock → 產生案件編號 → 圖片存 Drive → 寫入 Sheet → 釋放 Lock
5. 回傳案件編號給員工

**管理者處理：**
1. 輸入帳號密碼 → Apps Script 驗證雜湊 → 回傳 token（6 小時效期）
2. 前端存 token 於 sessionStorage，之後每次請求都附帶
3. 每個管理端 API 先驗證 token 有效性，再執行動作
4. 更新案件 → 自動記錄處理者、處理時間

**自動排程：**
- 每日 08:00 → 寄送「未處理案件清單」給所有管理者
- 每月 1 日 08:00 → 寄送「上月統計月報」給所有管理者

## 三、資料層設計（Google Sheet 分頁）

### 3.1 分頁：`回報資料`（Feedback）

| 欄位名稱 | 欄位代號 | 型別 | 說明 |
|---|---|---|---|
| 案件編號 | case_id | 文字 | `PCI-YYYYMM-NNN`，唯一，**所有查詢一律用此欄** |
| 提交時間 | submit_time | 日期時間 | 系統自動 |
| 工號 | emp_id | 文字 | 員工輸入 |
| 姓名 | emp_name | 文字 | 名冊自動帶入 |
| 語言 | lang | 代碼 | `ZH` / `ID`（員工提交時使用的語言） |
| 餐廳地點 | location_code | 代碼 | `LOC_02` 等，**存代碼不存文字** |
| 問題分類 | category_code | 代碼 | **可複選最多 2 項**，以逗號分隔如 `CAT_TASTE,CAT_HYGIENE`；<br>順序即點選順序，**第一個視為主要分類** |
| 問題描述 | description | 文字 | 選填（見 §6.2） |
| 滿意度評分 | rating | 數字 | 1–5 |
| 優先層級 | priority | 代碼 | `P_NORMAL` / `P_HIGH`（食安、異物等） |
| 圖片連結 | image_urls | 文字 | 多個連結以換行分隔（不再固定兩欄） |
| 處理狀態 | status_code | 代碼 | `ST_NEW` / `ST_PROC` / `ST_DONE` |
| 處理者 | handler | 文字 | 管理者姓名，系統自動帶入 |
| 處理回覆 | response | 文字 | 管理者填寫 |
| 處理時間 | response_time | 日期時間 | 系統自動 |
| 最後更新時間 | last_updated_at | 日期時間 | 系統自動（稽核用） |
| 最後更新者 | last_updated_by | 文字 | 系統自動（稽核用） |
| 提交識別碼 | client_submit_id | 文字 | 前端產生的 UUID，防重複提交 |
| 已刪除 | is_deleted | 布林 | **不刪列，改標記**（刪列會讓列號位移） |

> ⚠️ **重要原則：程式任何地方都不得用「列號」識別案件，一律以 `case_id` 查找。**

### 3.2 分頁：`員工名冊`（Employees）

| 欄位 | 型別 | 說明 |
|---|---|---|
| 工號 | 文字 | 唯一識別碼 |
| 姓名 | 文字 | 員工姓名 |
| 狀態 | 代碼 | `ACTIVE`（在職）/ `INACTIVE`（離職或異常）。**離職不刪除該列，改標記狀態**，這樣歷史案件仍查得到 |

**維護方式：** HR 每月匯出工號＋姓名的 CSV，貼上覆蓋此分頁（11,000 筆手動增刪不實際）。

**匯入後固定執行這兩支（在 Apps Script 編輯器裡）：**

| 函式 | 作用 |
|---|---|
| `normalizeEmployeeStatus()` | 把空白狀態補成 `ACTIVE`，並在狀態欄加上下拉選單 |
| `checkEmployeeRoster()` | 檢查前導零、重複、空白等問題（不會輸出姓名工號，結果可安全分享） |

> ⚠️ **貼上名冊前，務必先把「工號」整欄設定為「純文字」格式。**
> 若工號有前導零（如 `0012345`），Google Sheet 預設會當成數字而吃掉前面的 0，變成 `12345`，
> 導致員工輸入正確工號卻永遠比對不到。8,000 筆資料一旦貼錯，要重來一次很麻煩。
> 設定路徑：選取整欄 → 格式 → 數值 → 純文字 → 再貼上。

**查詢效能作法：**
1. 先查 `CacheService`（key = `emp:<工號>`，效期 6 小時）
2. 未命中則用 `createTextFinder(工號).matchEntireCell(true)` 在工號欄搜尋（Sheets 內建搜尋，不必讀取全部 8,000 列）
3. 找到後寫入快取

**名冊未涵蓋的處理：** 新進員工尚未進名冊時，允許手動輸入姓名並將該案件標記 `待確認工號`，避免員工完全無法回報。

## 四、多語系設計原則

**核心規則：資料庫只存代碼，顯示文字由前端依語言渲染。**

```
Sheet 存的值      →   中文介面顯示   /   印尼文介面顯示
LOC_02           →   第二餐廳       /   Kantin 2
CAT_HYGIENE      →   衛生環境       /   Kebersihan
ST_NEW           →   未處理         /   Belum Diproses
```

**為什麼這件事很重要：** 若直接存顯示文字，同一間餐廳在 Sheet 裡會同時出現「第二餐廳」和「Kantin 2」兩種寫法，統計會分成兩堆、篩選會漏掉一半。這個問題現在改是動兩行，上線後才發現要洗掉全部歷史資料。

**其他語言規則：**
- 介面文字統一放在 `js/i18n.js`，不散落在各個 HTML
- 語言偏好存 `localStorage`，員工下次掃碼直接進入慣用語言
- 記錄 `lang` 欄位，管理者可知道該用哪個語言回覆
- 員工自由輸入的「問題描述」與管理者的「回覆內容」不做翻譯，原文儲存

## 五、管理者帳號與登入機制

### 5.1 密碼儲存

```
註冊 / 改密碼時：
  salt = 隨機 16 字元字串（每人不同）
  hash = SHA-256 迭代 1000 次( salt + 密碼 )
  Sheet 只存 salt 與 hash，明文密碼不落地
```

### 5.2 登入流程

```
輸入帳號 + 密碼
    ↓
檢查該帳號是否被鎖定（連續失敗 5 次 → 鎖 15 分鐘）
    ↓
以該帳號的 salt 重算 hash，與 Sheet 比對
    ↓
  ┌─ 不符 → 失敗次數 +1，顯示「帳號或密碼錯誤」（不透露是哪個錯）
  └─ 相符 → 檢查狀態是否 ACTIVE
        ↓
     產生 token（UUID），存入 CacheService，效期 6 小時
        ↓
     回傳 token + 姓名 + 角色
        ↓
     前端存入 sessionStorage（關閉分頁即失效）
        ↓
     若「需重設密碼」= TRUE → 強制導向改密碼頁
```

### 5.3 後續請求驗證

每一支管理端 API 的第一件事都是驗證 token：token 不存在或已過期 → 回傳未授權 → 前端自動導回登入頁。

### 5.4 帳號管理（僅 SUPER 角色可見）

- 新增管理者（設定初始密碼，並自動標記「需重設密碼」）
- 停用／啟用管理者
- 重設他人密碼
- 調整角色

### 5.5 密碼規則

- 至少 8 字元，須含英文字母與數字
- 首次登入強制變更
- 忘記密碼由 SUPER 管理者重設（不做 email 自動重設，避免複雜度）

### 5.6 安全性注意

| 項目 | 作法 |
|---|---|
| 傳輸加密 | GitHub Pages 與 Apps Script 皆為 HTTPS，密碼傳輸已加密 |
| 前端原始碼公開 | 所有驗證邏輯**必須在後端**，前端不得有任何等同密碼的常數 |
| 管理端網址 | 不從員工端頁面連結，也不放進 QR Code，只私下提供給管理者 |
| Sheet 存取 | 管理者**不需要** Sheet 權限，一切透過介面操作 |

## 六、前端頁面規劃

### 6.1 員工端 — 首頁

- 語言切換：Bahasa Indonesia / 中文（存 `localStorage`，下次自動套用）
- 兩個大按鈕：
  - 提交回報（Lapor Masalah）
  - 查詢案件（Cek Status）

### 6.2 員工端 — 回報表單

| # | 欄位 | 必填 | 說明 |
|---|---|---|---|
| 1 | 工號 | ✅ | 輸入後即時比對名冊，成功自動帶入姓名並鎖定 |
| 2 | 姓名 | — | 自動帶入，唯讀 |
| 3 | 餐廳地點 | ✅ | 下拉選單，**可由 QR Code 參數預先選定** |
| 4 | 問題分類 | ✅ | 圖示 + 文字（🍜 口味 / 🧹 衛生 / 🙂 服務 / 🔧 設備 / 💡 建議）<br>**可複選，最多 2 項**；選滿後其餘選項變灰，需先取消才能改選 |
| 5 | 滿意度評分 | ✅ | 1–5 星 |
| 6 | 問題描述 | ❌ 選填 | **改為選填以降低放棄率**；**只要選項中含有「其他建議」就必填** |
| 7 | 圖片 | ❌ 選填 | 最多 2 張，前端壓縮後上傳 |

**QR Code 帶入地點：** 每間餐廳貼各自的 QR Code，網址帶參數（如 `?loc=LOC_02`），掃碼即自動選好地點——少一個操作步驟，且資料更準確。

**防重複提交：**
- 按下提交後立即禁用按鈕並顯示「傳送中…」
- 前端產生 `client_submit_id` 一併送出，後端若發現重複則不重複寫入

**提交成功畫面：** 成功訊息、案件編號（大字顯示）、提醒記下編號、〔繼續回報〕（保留工號姓名）、〔返回首頁〕
**提交失敗畫面：** 錯誤訊息、〔重新提交〕（資料保留不清空）

### 6.3 員工端 — 案件查詢

- 兩種查詢方式擇一：**案件編號**（單筆）或 **工號**（該員工全部歷史案件）
- 顯示：案件編號、提交時間、地點、分類、描述摘要、狀態（🔴 未處理 / 🟡 處理中 / 🟢 已結案）、管理者回覆
- **已指派處理者時，顯示處理者姓名**，方便員工知道找誰詢問；未指派則不顯示這一段。
  只顯示姓名、不顯示聯絡方式——查詢 API 不需登入，任何知道案件編號的人都看得到
- 工號查詢以列表呈現，點選展開詳情

### 6.4 管理者端 — 登入頁

**入口位置（已決定）：** 員工端首頁的**頁尾放一個低調的小連結**（例如角落的 `Admin` 小字）。

為什麼不藏起來：

> 前端原始碼在 GitHub 上是公開的，任何人都找得到 `admin.html` 的網址，
> 「藏起來」並不會比較安全。**真正的安全來自密碼雜湊、token、登入失敗鎖定。**
> 既然藏也藏不住，不如讓 6 位管理者方便一點——不用記長網址、不用怕書籤弄丟。

**所有管理者（含超級管理者）使用完全相同的介面**，差別只在登入後依角色決定
是否顯示「帳號管理」功能，不需要維護兩套介面。


帳號 + 密碼 → 驗證 → 進入案件列表（詳見 §5.2）

### 6.5 管理者端 — 案件列表

- 欄位：案件編號、提交時間、地點、分類、評分、狀態、處理者
- 篩選：地點 / 分類 / 狀態 / 日期範圍
- 排序：預設提交時間倒序
- **逾期標示：狀態為「未處理」且已超過 3 天者，整列標紅**
- 頂端顯示統計卡片：未處理 N 件 / 處理中 N 件 / 本月共 N 件

**檢視範圍（畫面最上方一條）：** 可選「全部時間」或某個月份，預設全部時間。
選單只列出真的有資料的月份，避免點到空白月份。

**三張統計卡片（未處理 / 處理中 / 已結案）全部跟著選定範圍。**
畫面上永遠只有一個尺度，範圍名稱就寫在卡片正上方，並顯示該範圍的總件數。
三張卡片相加必定等於總件數——這是使用者可以自己驗算的一致性。

> 早期版本是「未處理 / 處理中」算全部時間、第三張算本月，兩種尺度並排卻沒有標示，
> 實際使用時會誤判目前看的月份到底有幾件。

**唯一的例外是逾期提示列：** 它固定顯示**全系統**的逾期件數並明確標示，不跟著範圍走。
這是安全網——三個月前沒處理完的案子今天一樣要處理，被月份藏起來就永遠沒人發現。
點一下會跳到「全部時間 + 未處理」。

**重新整理按鈕**放在頁首標題旁，作用是「重新載入並回到剛登入的乾淨狀態」
（清除篩選、範圍回到全部時間、收合展開的案件）。
想保留目前條件重新抓資料，用篩選面板裡的〔查詢〕。

### 6.6 管理者端 — 案件詳情 / 回覆

- 完整案件資訊 + 圖片（點擊放大）
- 顯示員工使用的語言，提示該用哪個語言回覆
- 狀態下拉選單
- **指派處理者**（下拉選單，名單來自「選項設定」分頁的 `HANDLER` 類型；可不指派）
- 回覆內容輸入框 + **回覆範本一鍵帶入**（範本依案件分類篩選，內容取員工回報時的語言）
- 儲存（自動記錄處理者、處理時間、最後更新資訊）

**回覆為必填的狀態：** `處理中` 與 `已結案` 一定要有回覆內容才能儲存。
員工在查詢頁看得到狀態，狀態變了卻沒有說明，員工只會更想來問。

**「處理者」與「最後更新者」是兩個不同的欄位：**
處理者是被**指派**負責的人，最後更新者是實際按下儲存的人。
分開才查得出「這件事誰負責」與「這次是誰改的」。

**處理者名單放在「選項設定」分頁**（類型 `HANDLER`），不是「管理者名單」。

⚠️ **這兩份名單是完全不同的東西，不會互相同步（這是刻意的）：**

| | 管理者名單 | 選項設定的 `HANDLER` |
|---|---|---|
| 這些人是誰 | **使用這個 app 的人**：登入、看案件、回覆、結案 | **現場實際派工的人員**：廚房主管、清潔組長、維修人員 |
| 會不會碰到系統 | 會，要登入 | **不會**，他們只是被記錄為負責人 |
| 需要帳號密碼 | 要 | 不用 |
| 怎麼新增 | 帳號管理頁（僅 SUPER）或 `addAdminAccount()` | 在「選項設定」加一列 |

同一個人可以同時出現在兩份名單，但那是兩筆各自獨立的資料。
新增管理者**不會**自動變成可指派的處理者，反之亦然。

**處理者欄存的是代碼，不是姓名**（設計約定：存代碼不存顯示文字）。
顯示時才查最新姓名，這樣某人改名之後連歷史案件顯示的名字都會跟著更新。
離職時把「啟用」改成 `FALSE`，**不要刪除該列**，否則舊案件會查不到名字。

### ⚠️ CORS 實作規範（這一點一定會卡住，先寫清楚）

Google Apps Script **不支援 `doOptions`**，標準 CORS 解法在此行不通。唯一可行寫法：

- 前端 `fetch` 時 `Content-Type` 必須設為 `text/plain;charset=utf-8`
- **不得**加任何自訂 header（如 `Authorization`）
- JSON 字串直接放在 body，後端自行 `JSON.parse`
- token 放在 **body 內**，不放 header

### 統一回傳格式

```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "error": "EMP_NOT_FOUND", "message": "查無此工號" }
```

錯誤用代碼（`error`）判斷，訊息（`message`）交由前端依語言顯示。

### 產生邏輯（必須依此實作）

```

### 10.1 每日未處理清單（新增）

| 頻率 | 每日 08:00 |

### 10.2 每月統計月報

| 項目 | 設定 |
|---|---|
| 頻率 | 每月 1 日 08:00（統計上個月） |
| 收件人 | 同上（啟用中的超級管理者 ＋ `REPORT_TO` 額外名單） |
| 內容 | 上月回報總數 / 各餐廳數量 / 分類佔比 / 平均滿意度（整體 + 各餐廳） / 結案率 / 平均處理天數 / 未結案清單 |
| 空月份 | **照樣寄**（與日報相反）|

### ⚠️ 月報與日報的兩個差異（2026-08-22 實作時定案）

**1. 沒有資料時，日報不寄、月報照寄。**

日報是行動清單：每天寄一封「今天沒事」，兩星期後就沒有人會打開它了。
月報是紀錄：「上個月 0 件」本身就是資訊——可能真的很平靜，
也可能是 QR Code 被撕掉了、或根本沒人知道有這個系統。月報沒來的話，這兩種情況都會安靜地過去。

**2. 月報的「未結案」與日報的「未處理」不是同一件事。**

| | 定義 | 為什麼 |
|---|---|---|
| 日報 · 未處理 | 只有 `ST_NEW`（含狀態空白）| 問的是「今天先動哪一件」，處理中的已經有人在動了 |
| 月報 · 未結案 | 不等於 `ST_DONE`（含 `ST_PROC`）| 問的是「上個月的案子收尾了沒」，處理中也是還沒收尾 |

⚠️ 兩個數字本來就會不一樣。看到「日報說 3 件、月報說 5 件」不是 bug。

**月報另外多做一件規格沒寫的事：四格關鍵數字附上與前一個月的比較。**
單獨一個「本月 23 件」看不出好壞。只有方向明確的數字才上色
（滿意度、結案率越高越好）；**回報總數用灰色**——回報變多可能是問題變多，
也可能是員工更願意反映了，塗成紅色等於幫讀信的人下了一個沒有根據的結論。

### ⚠️ 複選對統計的影響（重要）

問題分類可複選最多 2 項，一筆案件可能同時計入兩個分類，
因此**「問題分類佔比」的總和會超過 100%**。統計時必須明確採用哪一種口徑：

| 口徑 | 算法 | 適合看什麼 |
|---|---|---|
| **按出現次數** | 每個被選到的分類都計 1 次 | 哪一類問題最常被提到 |
| **只算主要分類** | 只計 `category_code` 的第一個代碼 | 案件性質分布、派工歸屬 |

程式已保留點選順序，兩種統計都做得出來。
建議 Dashboard 兩種都呈現，並在圖表標題註明採用哪一種。

**管理端的分類篩選要注意：** 條件是「**包含**某分類」，不是「等於」。

### ⚠️ 收件人規則（2026-08-22 修訂）

原本寫的是「所有 ACTIVE 管理者」，實際運作改為：

> **啟用中的超級管理者 ＋「選項設定」分頁裡類型為 `REPORT_TO` 的額外地址**

理由是實際流程為「超級管理者看完再交辦」，一般管理者不需要每天收到全廠清單。

額外名單與處理者名單同一套作法（設計約定第 7 條）：加一列、啟用打勾就生效，
不想寄了把啟用改成 FALSE，不必刪那一列也不必改程式。
`REPORT_TO` 的**代碼欄放的是 Email 地址**（其他類型放的是識別碼），
中文顯示欄放用途說明（廠長、秘書…）。

**同一個信箱只會收到一封**——兩個管理者帳號填同一個 Email 是常見情況，系統會自動去重。

⚠️ **這個決定有連帶影響：日報是「今天該處理哪些案件」的行動清單。**
一般管理者收不到，就不會主動知道有什麼要處理，派工責任落在超級管理者身上。
哪天改成讓一般管理者自行認領案件，這裡要改回去。

## 十一之前補充：資料保存政策（2026-08-22 實作定案）

| 項目 | 內容 |
|---|---|
| 政策 | 結案滿 **13 個月**去識別化 |
| 清掉 | 工號、姓名、照片 |
| 留著 | 案件編號、時間、地點、分類、評分、狀態、描述、回覆 |
| 起算點 | **結案時間**（不是提交時間）——一直沒結案的不清除，那代表問題還沒解決 |
| 頻率 | 每月 1 日 05:00（備份之後、月報之前）|

**不整筆刪除的理由：** 隔年要做「今年 vs 去年同期」的比較時，整筆刪掉就沒資料了。

⚠️ **工號與姓名一定要一起清。** 只刪照片、留著姓名不叫去識別化——
姓名本來就是最直接的個資。

### 規格外補上的一個漏洞

**軟刪除的案件用「提交時間」起算。** 它不會再被結案，
用結案時間算的話永遠不會到期，那筆個資就會一直留著。

### 實作上做不到的部分（誠實記錄）

清掉工號姓名之後，**Google 試算表的「版本紀錄」裡還看得到清除前的內容**。
要真正抹掉只能「另存新檔 + 刪掉舊檔」重置歷史。
目前的緩解是管理者不需要 Sheet 權限（§5.6），只有擁有者進得去。

### 備份與去識別化的關係

**備份刻意不含照片。** 備份照片會讓去識別化失效——
照片一張都沒消失，只是換個資料夾放。
照片的救援改用 Drive 垃圾桶的 30 天窗口，時間到 Google 自己永久刪除。

**備份只保留最近 3 份。** 備份裡有工號、姓名與整份員工名冊，
永遠留著的話，「滿 13 個月去識別化」就變成做做樣子。

## 十一、安全性與防護

| 風險 | 對策 |
|---|---|
| 未授權存取管理端 | token 驗證 + 密碼雜湊 + 登入鎖定（§5） |
| 惡意灌水 | 同一工號每日提交上限 10 筆 |
| 重複提交 | `client_submit_id` 去重 + 按鈕禁用 |
| 工號被列舉 | 驗證 API 加上每 IP 每分鐘次數限制；查無工號的回應統一訊息 |
| 資料誤刪 | 一律軟刪除（`is_deleted`）；每月自動複製一份 Sheet 存檔 |
| 個資保護 | 結案滿 13 個月自動去識別化（見 §11.1）；管理者不開放 Sheet 直接存取 |

### 11.1 資料保存政策：結案滿 13 個月去識別化

**規則：案件結案（`ST_DONE`）滿 13 個月後，自動清除其中的個資，但保留案件本身。**

| 欄位 | 處理 | 為什麼 |
|---|---|---|
| 工號、姓名 | **清空** | 這才是真正的個資 |
| 圖片 | **從 Drive 刪除，連結清空** | 照片可能拍到人 |
| 案件編號、提交時間、地點、餐別、分類、評分、狀態 | 保留 | 統計要用 |
| 問題描述、處理回覆、處理者 | 保留 | 有參考價值，且通常不含個資 |
| 處理時間、最後更新資訊 | 保留 | 稽核用 |

**為什麼是「去識別化」而不是「整筆刪除」：**

整筆刪掉的話，隔年想做「今年 vs 去年同期」的比較就沒有資料了。
去識別化能同時滿足個資保護與統計需求——個資消失，但那個月有幾件、
哪間餐廳、什麼問題、幾顆星，全部留著。

**⚠️ 容量從來不是做這件事的理由。** 實際推算：

| 項目 | 13 個月後 | 佔用比例 |
|---|---|---|
| Sheet 格數 | 650 筆 × 20 欄 = 13,000 格 | 上限 1,000 萬格的 0.13% |
| Drive 照片 | 約 68 MB | 免費 15 GB 的 0.45% |

就算十年不清也只用掉 1.2%。**做這件事純粹是為了個資保護。**

**計算起點是「結案時間」，不是提交時間。** 一直沒結案的案件不會被清除——
那代表問題還沒解決，資料還要用。

**實作排在第 4 階段**，與每日 / 每月排程共用同一套觸發器機制。

## 十二、錯誤處理原則

1. 後端每支 API 都以 `try / catch` 包覆，例外一律寫入 `錯誤日誌` 分頁
2. 前端不顯示技術訊息，只顯示使用者看得懂的文字（依語言）
3. 網路失敗時保留已填內容，讓使用者可直接重試而不必重填
4. 所有載入中狀態都要有視覺回饋（避免使用者重複點擊）

```
KANTIN/
├─ index.html                員工端首頁       ┐
├─ report.html               回報表單         │
├─ query.html                案件查詢         │ 前端檔案必須放在根目錄
├─ admin.html                管理端           │ （GitHub Pages 的限制）
├─ css/style.css                              │
├─ js/                                        │
│   ├─ config.js             ← API 網址集中一處 │
│   ├─ i18n.js               ← 中文 / 印尼文對照│
│   ├─ api.js                ← 所有 API 呼叫   │
│   └─ image.js              ← 圖片壓縮        ┘
├─ .nojekyll                 關閉 GitHub 的 Jekyll 處理，不可刪除
├─ CLAUDE.md                 給 AI 助手的專案說明
├─ docs/
│   ├─ 規格書_v2.md
│   ├─ 開發進度.md
│   ├─ 部署筆記.md            ← 記錄網址、部署步驟、踩過的坑
│   └─ 管理者操作手冊.md
├─ gas/                      ← Apps Script 程式碼備份
│   ├─ Main.gs               路由
│   ├─ Feedback.gs           回報相關
│   ├─ Admin.gs              管理者相關
│   ├─ Auth.gs               密碼與 token
│   ├─ Report.gs             日報月報
│   └─ Utils.gs              共用工具
└─ tools/dev-server.js       本機開發伺服器

**要點：**
- **前端檔案一定要在根目錄。** GitHub Pages 只能從 `/(root)` 或 `/docs` 發布，

- `.nojekyll` 不可刪除，否則 GitHub 會用 Jekyll 處理檔案，可能造成非預期行為
- API 網址只寫在 `js/config.js` 一處，換部署網址時只改一行
- Apps Script 線上編輯器沒有版本控制，**每次改完都複製一份到 `gas/`**

## 十五、部署與維運注意事項

### ⚠️ Apps Script 重新部署的陷阱

改完程式後，必須走：**管理部署作業 → 編輯（鉛筆）→ 版本選「新增版本」→ 部署**

若按了「新增部署作業」，**網址會改變**，前端就連不上了——這是最常見、最花時間找的錯誤。

### 開發 / 正式環境分離

建立兩份 Sheet（開發用、正式用），在 `Utils.gs` 用一個常數切換。測試產生的垃圾資料才不會混進正式統計。

### 日常維運分工

| 工作 | 頻率 | 負責人 | 方式 |
|---|---|---|---|
| 處理案件 | 每日 | 管理者 | 管理介面 |
| 更新員工名冊 | 每月 | HR / 管理者 | 貼上 CSV 至 Sheet |
| 新增管理者 | 需要時 | SUPER 管理者 | 帳號管理頁 |
| 新增餐廳 / 分類 | 需要時 | 管理者 | `選項設定` 分頁加一列 |
| 新增回覆範本 | 需要時 | 管理者 | `回覆範本` 分頁加一列 |
| 檢查錯誤日誌 | 每月 | 系統維護者 | `錯誤日誌` 分頁 |

### 管理者可否直接編輯 Sheet

| 分頁 | 可否直接改 |
|---|---|
| 員工名冊 / 選項設定 / 回覆範本 | ✅ 可以，這是預期的維護方式 |
| 回報資料 | ❌ **不要**——直接改不會記錄處理時間與稽核欄位，統計會失真 |
| 管理者名單 | ⚠️ 密碼欄位絕不可手改，請用帳號管理頁 |
