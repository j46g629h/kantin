### ⚠️ 線上事故 2：登入成功後立刻被彈回登入頁

**症狀：** 帳號密碼輸入正確、沒有任何錯誤訊息，但畫面又回到登入表單。

**原因：`CacheService` 在這個專案上完全失效。**
`put()` 不會丟出任何錯誤，但 `get()` 永遠回傳 null——
連同一次請求內寫完立刻讀都讀不到。實測確認（`PropertiesService` 完全正常）。

token 就存在 CacheService 裡，所以：登入成功 → 發出 token → 下一個請求讀不到 →
回傳未授權 → 前端清除登入狀態並導回登入頁。

**為什麼拖到現在才發現：** 快取失效通常只會「變慢」，功能還是對的。
選項快取與員工快取其實早就沒在運作，只是每次都重讀 Sheet，沒人看得出來。
直到 token 也依賴它，才變成功能性故障。而且因為 `put()` 不報錯，錯誤日誌裡一片空白。

**修正：** 新增 `gas/Store.js`，用 `PropertiesService` 實作附有效期的鍵值儲存，
所有原本用 `CacheService` 的地方（token、登入失敗計數、選項快取、員工快取）全部改用它。

**額外好處：** Properties 存的 token 是真的刪得掉的，
「登出」因此變成真正的伺服器端登出，而不是只清掉瀏覽器那一份等它自己過期。

**實測驗證（不需帳密，用一次性假帳號打正式 API）：**

| 測試 | 修正前 | 修正後 |
|---|---|---|
| 連續登入失敗的計數跨請求累加 | 永遠停在「還可以試 4 次」 | 4 → 3 → 2 ✅ |
| 連續失敗 5 次後鎖定 15 分鐘 | 從未生效 | 第 6 次正確回 `LOGIN_LOCKED` ✅ |

登入失敗鎖定用的是同一套儲存機制，所以它能跨請求累加，就代表 token 也存得住。

### ⚠️ 線上事故 1：加了欄位定義就部署，導致完全無法登入

**超級管理者完全無法登入**（回「系統出了問題」）。

**原因：** 把「電話」加進 `ADMIN_COLUMNS`（欄位定義）之後就直接部署了，
但 Sheet 上還沒有那一欄——`getAdminColumnMap()` 找不到欄位就丟出例外，
於是每次讀管理者名單都失敗，連登入都進不去。

**教訓：改欄位定義等於改資料結構，不可以先部署再叫使用者跑升級程式。**
順序必須是「先升級 Sheet，再部署程式」，或是讓新欄位為選填。
這次因為需求本來就不需要電話，直接把欄位拿掉是最乾淨的解法。

**同時修掉一個同源的隱患：** `writeRowByColumns()` 原本是照欄位定義的順序

### ⚠️ 期間抓到的真實漏洞：選填欄位讓「新增管理者」在升級前是壞的

`writeRowByColumns()` 會走過**所有**欄位定義，包含標了 `optional` 的。
Sheet 還沒升級時 `colMap.password_changed_at` 是 `undefined`，
而真實 Apps Script 的 `getRange(row, undefined)` 會直接丟例外——
也就是說，從部署 @29 到使用者跑完升級的那段時間，**「新增管理者」整支是壞的**。

諷刺的是，`optional` 這個機制本來就是為了消滅這種空窗期，
結果自己在呼叫端留了一模一樣的洞。

**修法：** `writeRowByColumns()` 遇到 colMap 裡沒有的欄位就跳過。

**為什麼差點漏掉：** 本機測試的假 Sheet 對 `getRange(row, undefined)`
默默接受（陣列索引 `[NaN]` 不會報錯），一路綠燈。
已把假 Sheet 改成跟真的一樣「欄號不合法就丟例外」，
並實測驗證過：把修正拿掉，測試會紅（`getRange 收到不合法的位置: row=7, col=undefined`）。

**教訓：假的服務對錯誤輸入太寬容，等於把測試變成裝飾品。**

### 為什麼「顯示目前密碼」做不到

Sheet 存的是加鹽 + SHA-256 迭代 1000 次的結果，**這個運算單向不可逆**——
不是系統不給超級管理者看，是連系統自己都算不回去。

要能顯示，唯一辦法是改成存明文。那樣任何拿到這份 Sheet 的人
（Google 帳號被盜、誤設分享、Google 端備份）就直接拿到全部管理者的密碼，
包括超級管理者自己那組。這條路沒有走。

替代方案是「密碼最後變更時間」：剛重設完那一列就會顯示剛剛的時間，
正好回答真正想確認的事——「我剛剛的操作有沒有生效」。

### 「待本人自行設定密碼」標籤的正確含意

那個標籤反映的是 `需重設密碼 = TRUE`，意思是
**「這組密碼是別人幫他設的，他本人還沒換成只有自己知道的」**。

超級管理者剛幫某人重設完密碼，這個標籤**本來就該出現**——
不然「首次登入強制改密碼」的機制就失效了。
原本寫成「尚未改過初始密碼」，讓人誤以為自己剛才的操作沒生效，已改掉。

### 新欄位怎麼加才不會重演線上事故 1

「密碼最後變更時間」是這個專案第一個標成 **`optional: true`** 的欄位。

`buildColumnMap()` 現在遇到標了 optional 又找不到的欄位會直接跳過，不丟例外。
所以**先部署程式、後跑升級**是安全的：升級前那一欄不顯示，其他功能完全正常，
沒有「部署到升級之間功能全壞」的空窗期（那正是事故 1 的成因）。

實際驗證：部署 @29 之後、還沒跑升級程式時，用假帳號打線上 `adminLogin`
回的是 `LOGIN_FAILED`（正常的帳密錯誤）而不是 `SERVER_ERROR`。

⚠️ 代價是呼叫端一定要自己檢查 `if (colMap.xxx)`，因為欄號可能是 `undefined`。
漏了的話 `getRange(row, undefined)` 會炸——
等於把問題從「部署當下全壞」搬到「某個功能被用到時才壞」，更難查。

### ⚠️ 上線時踩到：新增需要新權限的功能，第一次執行必定失敗

加了寄信功能後第一次執行 `sendDailyReportNow()`，授權畫面明明按過了，
卻回「已寄出 0 封（失敗 2 封）」，看起來像兩個信箱都有問題。

真正的原因是 `MailApp.sendEmail` 需要 `script.send_mail` 權限，而
**Apps Script 是掃描程式碼推算需要哪些權限的**——剛推上新程式碼時
它可能還在用舊的權限清單。**再執行一次就好**，第二次的授權畫面才會包含新權限。

真正浪費時間的不是那個權限（那是正常行為），是**訊息看不出問題在哪**。
已修正：`isAuthorizationError()` 會把授權錯誤跟一般寄信失敗分開，
執行紀錄直接寫「請再執行一次這支函式」。

同時新增兩支維運工具，後面 4-4（Drive 權限）與 4-5（刪檔權限）一定會再用到：

| 函式 | 用途 |
|---|---|
| `showRecentErrors()` | 把錯誤日誌最近 5 筆完整印在執行紀錄上（在儲存格裡讀堆疊訊息幾乎不可能）|
| `checkMailSetup()` | 把額度 / 收件人 / 產生信件內容 / 實際寄信拆成四項各測一次，才分得出是權限問題還是內容程式出錯 |

### 關卡 4-2 之後的追加調整（第三批）✅ — 動態表輸出 PDF

**⚠️ 使用者原本要的是「輸出成圖片」，改做列印 / PDF。**

實際收到 7 月月報之後提出的兩項：

| # | 需求 | 處理 |

**⚠️ 這件事真正的難點不是排版，是「同一份資料抄在兩個地方」。**

系統資訊本來只放在前端 `js/config.js` 的 `SYSTEM_INFO`，
但信是 Apps Script 產生的，而**它讀不到 GitHub Pages 上的前端檔案**。

考慮過三種作法：

| 作法 | 為什麼不採用 |
|---|---|
| 寄信時上網抓 `js/config.js` | 多一個會失敗的網路請求，只為了三行不會變的文字 |
| 放進「選項設定」分頁 | 版本號是跟著改程式碼變動的，而改程式碼的人不會順手去改 Sheet，一樣會走鐘（而且更容易被忘記）|
| **複製一份到 `gas/Config.js` + 寫測試盯著** | ✅ 採用 |

**為什麼「印錯的版本號」比「不印版本號」還糟：**
版本號存在的理由就是排查——有人回報問題時先問他看到的版本。
印錯的話，你會拿著錯的版本號去查錯的那一版程式碼，比沒有線索更浪費時間。

所以新增 `tools/test-version-sync.js`（25 項），一次盯四件事：

1. 七個 HTML 的 `?v=` 是否一致
2. 同一個 HTML 裡有沒有出現兩種版本號（CSS 帶 2.7、JS 帶 2.6 的話只有一個會更新）
3. `js/config.js` 與 `gas/Config.js` 的 `SYSTEM_INFO` 是否完全相同（版本 / 年份 / 維護單位中印 / 聯絡方式）
4. 前端頁尾顯示的版本，是否就是 HTML 實際載入的那一版

⚠️ 寫這支測試時差點做出一個**永遠會過的測試**：正規表示式失效時兩邊都讀成 `null`，
而 `null === null` 是相等的，於是每一項都通過，但它其實什麼都沒有比對到。
已加兩行「先確認真的讀得出東西來」。**永遠會過的測試比沒有測試更危險。**

驗證方式：故意把 `gas/Config.js` 的版本改成 `v9.9`，確認測試真的紅了，再改回來。

| 連結自己指定 `color` 與 `text-decoration` | 不靠預設 | Gmail、Outlook 會把沒指定顏色的 `<a>` 一律改成藍色底線，整片灰色的頁尾會突然冒出一條藍字 |

### 關卡 4-4：每月自動備份 ✅

- ✅ `gas/Backup.js`：`backupMonthly()` / `backupNow()` / `listBackups()` / `latestBackupInfo()`
- ✅ `gas/Triggers.js`：加入「每月 1 日 02:00」的排程
- ✅ 本機測試 `node tools/test-backup-api.js`（30 項）
- ✅ 已部署 `@36`
- ✅ **`installTriggers()` 已執行**，`listTriggers()` 確認三支排程都在
- ✅ **`backupNow()` 實測成功**，Drive 已出現備份

**做法：** 每月 1 日凌晨 02:00 把整份 Sheet `makeCopy()` 到 Drive 的「備份」資料夾，
檔名 `備份_yyyy-MM-dd_HHmm`，只保留最近 3 份，舊的丟垃圾桶。

**⚠️ 先講清楚這個備份在防什麼，不然會誤以為保護範圍比實際大：**

| | |
|---|---|
| ✅ 防得住 | 手滑改壞幾列、刪掉一整個分頁、程式出錯寫壞資料、**去識別化清掉了不該清的東西** |
| ❌ 防不住 | 整個 Google 帳號出事（被盜、被停用）。備份跟正本在同一個 Drive、同一個帳號底下，帳號沒了就一起沒了 |

要補上那個缺口只能把檔案放到 Google 以外的地方，而那需要付費服務或每個月有人手動下載。
以每月 50 筆的規模不值得，**但要知道有這個缺口。**

**設計決策：**

| 項目 | 作法 | 為什麼 |
|---|---|---|
| **只備份 Sheet，不備份照片** | | 備份照片會讓 4-5 的去識別化失效——照片一張都沒消失，只是換個資料夾放，等於白做。而且照片是最佔空間的東西，複製一份容量直接翻倍 |
| 照片的救援改用 Drive 垃圾桶 | 4-5 用 `setTrashed(true)` | **垃圾桶保留 30 天**，這期間隨時救得回來，30 天後 Google 自己永久刪除。零維護、不佔額外空間，而且時間到了是真的刪掉——正是個資政策要的效果 |
| **只保留 3 份** | 不是留越多越好 | 備份裡有工號、姓名與整份員工名冊。永遠留著的話，「滿 13 個月去識別化」就變成做做樣子：正本清乾淨了，備份裡那份個資還在 |
| 清舊備份也是丟垃圾桶 | 不永久刪 | 保留份數萬一設錯，垃圾桶裡還有 30 天可以救 |
| **只刪檔名開頭是 `備份_` 的檔案** | | 使用者可能自己放東西進那個資料夾。「自動清理」誤刪使用者的檔案是這個功能最不能發生的事——而且平常完全看不出來，直到某天有人發現檔案不見了。測試裡特地放了 `備份說明.txt`（開頭很像但不是）確認不會被誤刪 |
| 備份資料夾用「圖片資料夾的上一層」找 | 不另外記一組 ID | 多一個要手動填的 ID，就多一個換人接手時會填錯的地方 |
| 存成 Sheet 副本，不是 xlsx | | 還原時直接打開、把需要的列複製回去就好，不必匯入匯出 |
| 失敗要往外丟例外 | 不吞掉 | 備份失敗如果安靜地過去，等到真的需要它的那天才發現沒有，就太遲了 |
| 多一支 `listBackups()` | | 「備份到底有沒有在跑」的檢查點。排程壞掉時畫面上不會有任何跡象，只有最新那份的日期停著不動——所以超過 40 天就主動提醒 |

**⚠️ 同一天的排程，時間一定要錯開，而且要照該有的順序排。**

同一個小時的兩個觸發器**沒有先後順序保證**（Google 自己調度）。
備份如果排在去識別化後面才跑，備到的就是已經被清掉的資料，
安全網等於不存在，而且完全看不出來哪裡不對。

每月 1 日目前的順序：

| 時間 | 排程 | |
|---|---|---|
| 02:00 | `backupMonthly` | 先把安全網架好 |
| 05:00 | （4-5 去識別化） | 規劃中 |
| 08:00 | `sendMonthlyReport` | 再寄上個月的統計 |

**光靠時間排序是不夠的。** 萬一備份那次剛好失敗，時間再怎麼排也沒用——
所以 `latestBackupInfo()` 這一支是特地為 4-5 準備的：
**動手刪資料之前先確認安全網在，沒有近期備份就拒絕執行。**
它在 Drive 讀不到的時候也回傳 `null` 而不是丟例外，
因為「讀不到」絕對不可以被當成「有備份」。

⚠️ **備份檔裡有工號、姓名與整份員工名冊（約 11,000 筆個資）。**
絕對不可以分享給任何人，也不要下載後隨手放在桌面。

### 關卡 4-5：結案滿 13 個月去識別化 ✅

- ✅ `gas/Retention.js`：`previewDeidentify()` / `deidentifyMonthly()` / `deidentifyNow()`
- ✅ `gas/Triggers.js`：加入「每月 1 日 05:00」的排程
- ✅ 本機測試 `node tools/test-retention-api.js`（68 項）
- ✅ 已部署 `@37`
- ✅ **`previewDeidentify()` 試跑通過** — 顯示「沒有任何案件到期」（系統 2026 才上線，符合預期）
- ✅ **`installTriggers()` 已執行**，`listTriggers()` 確認四支排程都在
- ⏳ **真正清到第一筆資料要等 2027 下半年。** 到時候先跑一次 `previewDeidentify()`
      把名單看過，不要直接讓排程自己動手

**做什麼：** 清掉工號、姓名、照片；留著編號、時間、地點、分類、評分、狀態、描述、回覆。

**⚠️ 這是整個系統唯一會永久破壞資料的功能，所有設計都繞著這件事轉。**

**四道安全機制（缺一不可）：**

| # | 機制 | 擋掉什麼 |
|---|---|---|
| 1 | **試跑模式** `previewDeidentify()` | 只列名單，一個字都不改。這種功能出錯的樣子不是跳錯誤訊息，而是「安靜地清掉不該清的東西」，而且很久以後才會發現 |
| 2 | **沒有近期備份就拒絕執行** | 光靠「備份排 02:00、這支排 05:00」不夠——萬一那天的備份剛好失敗，時間再怎麼排也沒用 |
| 3 | **照片丟垃圾桶，不永久刪** | 判斷錯了還有 30 天可以救；30 天後 Google 自己永久刪除 |
| 4 | **分界日往保守方向夾齊** | 寧可晚一個月刪，也不要早一天刪。晚了下次補上，早了回不來 |

**設計決策：**

| 項目 | 作法 | 為什麼 |
|---|---|---|
| 工號與姓名一定要一起清 | 不是只刪照片 | **姓名本來就是最直接的個資。** 只刪照片留著姓名，等於窗簾拉上但大門敞開，那不叫去識別化 |
| 起算點是結案時間 | 不是提交時間 | 一直沒結案的案件不清除——那代表問題還沒解決，資料還在用 |
| **軟刪除的用提交時間算** | **規格外自己加的** | 軟刪除的案件不會再被結案，用結案時間算的話它永遠不會到期，那筆個資就一直留著。這是規格沒想到的漏洞 |
| 已結案但沒有結案時間 → 報出來，不碰 | 不默默跳過 | 默默跳過的話，那些案件會永遠不被清，而且沒有任何人知道。報告會列出編號請人手動補 |
| 先丟照片，再清欄位 | 順序不可顛倒 | 反過來的話，清完欄位才丟照片失敗，Sheet 裡的連結已經沒了，那幾張照片會變成沒人知道存在的孤兒檔案，永遠留在 Drive——那正是這功能要消滅的東西。反過來則下個月會自動補上 |
| 稽核紀錄借用「最後更新時間 / 最後更新者」 | 不新增欄位 | 加欄位就要升級 Sheet，而改欄位定義是這個專案踩過最痛的坑（設計約定第 12 條）。這兩欄本來的語意就是「最後是誰、什麼時候動了這筆」，系統自己動的也算 |
| 已清乾淨的不重複寫 | | 重複寫沒壞處，但會把「最後更新時間」每個月往前推一次，看起來像這筆資料一直被人動 |
| 分界日用純整數月份加減 | 不用 `new Date(y, m-13, d)` | 後者會用到伺服器時區，而日期是依專案時區算的，跨日那幾小時會算到隔壁天 |
| 單次上限 300 件，**並且明說還剩幾件** | | 只寫「已處理 300 件」看起來像做完了，其實還剩一大堆 |

**⚠️ 一個做不到的部分，誠實記著：**

清掉工號姓名之後，**Google 試算表的「版本紀錄」裡還看得到清除前的內容**。
要真正抹掉只能「另存新檔 + 刪掉舊檔」重置歷史。
目前的緩解是管理者根本不需要 Sheet 權限（規格 §5.6），只有擁有者進得去。
這不是程式能解決的事，但不該假裝它不存在。

**測試的重點刻意放在「不該動的有沒有被動到」**（68 項裡有一整段專門測這個）：
功能沒做到（該清的沒清）下個月就補上了，但清錯了是回不來的。
所以「未結案不可碰」「處理中不可碰」「晚分界日一天不可碰」「沒有結案時間不可碰」
比「有沒有清乾淨」重要得多。

**每月 1 日的完整順序：**

| 時間 | 排程 | |
|---|---|---|
| 02:00 | `backupMonthly` | 先把安全網架好 |
| 05:00 | `deidentifyMonthly` | 再清掉滿 13 個月的個資 |
| 08:00 | `sendMonthlyReport` | 最後寄上個月的統計 |

⚠️ 同一個小時的兩個觸發器**沒有先後順序保證**，所以一定要錯開小時。

### 關於「結案滿 13 個月去識別化」

**清除工號、姓名、照片；保留編號、時間、地點、分類、評分、狀態、描述、回覆。**

為什麼不整筆刪除：隔年要做「今年 vs 去年同期」的比較時，整筆刪掉就沒資料了。
去識別化能同時滿足個資保護與統計需求。

⚠️ **容量不是理由。** 13 個月的資料只佔 Sheet 上限的 0.13%、Drive 的 0.45%，
十年不清也只用掉 1.2%。這件事純粹是為了個資保護（規格 §11）。

計算起點是**結案時間**，不是提交時間——一直沒結案的案件不清除，
那代表問題還沒解決。

排在這一階段是因為要跟每日 / 每月排程共用同一套觸發器機制，一起做才不會重複工。

## 第 5 階段：介面設計與美化

**為什麼獨立成一個階段（2026-08-22 決定）**

設計跟功能的「完成」不是同一回事。功能有明確的完成點——測試過了、實測過了、部署了，
就不會再回頭。**設計不是，它會一直被回頭修改。**

這件事在這個專案已經有前例：關卡 4-2（動態表）後面掛了**三批**「之後的追加調整」，
內容全部都是可讀性與版面。那些調整沒有更好的地方放，只好一直往同一個關卡後面接。

把設計獨立出來，那些反覆的調整才有自己的家，
而且**「上線」這個階段才有可能真的完成**——
否則每次改個顏色都算在上線階段裡，上線就永遠差一點。

---

### ⚠️ 這個階段最大的風險：永遠做不完

設計是典型的無底洞。「再調一點就更好」可以無限進行下去，
而**每多調一天，上線就晚一天**——但員工餐廳的問題並不會等你把顏色調好。

所以這個階段有三條硬規定：

**1. 分成兩批，只有第一批擋上線**

| 批次 | 內容 | 擋不擋上線 |
|---|---|---|
| **定調 + 套用**（5-1～5-4） | 主色、輔色、字體、圖示、主視覺，並套到所有頁面 | ✅ **擋** |
| **打磨**（5-5） | 動畫、空狀態插圖、深色模式、微調 | ❌ **不擋，上線後慢慢做** |

**2. 定案之後就凍結**

主色、輔色、字體、圖示風格一旦在 5-1 選定，**後面只做不影響識別的微調**。
要再動這四項就是重來一次，不是「順便改一下」。

**3. 每個關卡都要有驗收方式**

跟前面四個階段一樣：說得出「怎樣算做完」才能往下一關。
設計沒有測試可以跑，所以驗收方式一律是**在真實手機上看過**。

### 現況診斷：為什麼現在的介面顯得單調

`css/style.css` 的架構其實是好的——顏色、圓角、字級、間距全部集中在開頭的 `:root`，
所以**改那 40 行就能改變整個 app**，不必逐頁去找。問題不在技術。

單調的原因是這五個：

| # | 原因 | 現況 |
|---|---|---|
| 1 | 只有一個顏色 | 全部是 `#2563eb`，那是每個後台模板都在用的通用藍。沒有輔色、沒有強調色 |
| 2 | 沒有品牌識別 | 沒有 logo、沒有照片、沒有插圖。首頁主視覺是一個 🍽️ emoji |
| 3 | **所有元素視覺重量一樣** | 每張卡片都是白底 + 1px 邊框 + 同樣圓角 + 極淡陰影。連「主要」卡片也只差在邊框粗 1px，眼睛沒有落點 |
| 4 | 用 emoji 當圖示 | 🍽️ 📝 🔍 在 iPhone、三星、小米上長得都不一樣，讀起來像還沒做完的暫代品 |
| 5 | 間距沒有節奏 | 幾乎所有地方都是 `gap:12px`、`padding:16~20px`。均勻＝平淡 |

**第 3 點是關鍵。** 單調的本質不是「顏色不夠多」，是**「沒有東西比別的東西重要」**。

### 四個容易漏掉的連帶影響

改配色不是只有改 CSS，這四個地方會跟著出問題：

| 地方 | 為什麼會漏 |
|---|---|
| **信件樣式** | `gas/Notify.js` 的顏色是寫死在每個標籤的 `style=` 上的（信箱軟體會丟掉 `<style>` 區塊）。改了 app 沒改信，日報月報會變成另一套配色 |
| **PDF 輸出** | 動態表的列印樣式是另一套規則。**列印時的斷點必須寫成 `@media screen and (max-width: ...)`**，裸的 `(max-width: 700px)` 在列印時會被誤觸發，印出來變手機版 |
| **資源版本號** | 設計階段會改很多次前端檔案，每一批改完都要跑 `node tools/test-version-sync.js`（九個地方要一致）。**一批改完 bump 一次就好，不要每調一個顏色就 bump** |
| **GitHub Pages 快取** | Pages 有 10 分鐘快取，設計期間一律用 `node tools/dev-server.js` 在本機看，不要推上去再看，否則會分不清是「沒改到」還是「快取還沒過」 |

試辦（第 6 階段）會找 349 位真實員工使用。
**他們看到的應該是最終版本**——等他們用了舊版再改，等於浪費一次真實回饋的機會。

而 5-5（打磨）刻意排在上線之後：那一批本來就要靠試辦的回饋才知道要調什麼。

### 關卡 5-1：設計定調 ✅

**方向 A 定案：中性米白底 + 近黑主動作 + 顏色只給有意義的東西。**

參考網站是使用者提供的 [madebypan.com](https://madebypan.com)。
掃過它每一個元素之後發現一件關鍵的事：**整站零飽和色**——
它的「好看」完全不是靠顏色，而是靠暖中性底、極端字級落差、膠囊形狀、
幾乎沒有邊框，以及「絕大多數東西完全平坦、少數幾個給很重的陰影」。

| 項目 | 定案 |
|---|---|
| 底色 | `#EFEFED` 中性米白（不是白、也不是冷灰）|
| 主要動作 | 近黑 `#1A1A1C`，**無漸層** |
| 陰影 | **兩階**：可點區塊淡陰影、主要動作重陰影、一般卡片平坦 |
| 標誌 | **W1-b** 純文字（PCI 大加粗 + GA 縮小拉開字距）|
| 字體 | 維持現有，字級改用 `clamp()` |
| 深色模式 | 擋掉（`color-scheme: light`）|

**⚠️ 為什麼不能照抄零飽和色：** 這個 app 的狀態色（未處理紅 / 處理中黃 / 已結案綠）
與星等**帶著意義**，拿掉就看不懂了。所以改成「中性底 + 顏色只給意義」——
畫面上只要有顏色就一定代表什麼，那幾個顏色反而比原本更跳。

**⚠️ 為什麼主要按鈕不加漸層（使用者問過）：** 參考網站全站沒有漸層，
而且**「漸層 + 光澤」正是 pci 藍球看起來過時的原因**——使用者自己否決過那個風格。

**設計決策：**

| 項目 | 作法 | 為什麼 |
|---|---|---|
| 品牌藍只出現在 logo 與焦點外框 | 不進介面 | app 已有紅黃綠橙四種功能色，再加第五種暖色會互相打架。走純中性反而讓那幾個顏色更明顯 |
| 陰影分兩階，不是平均給 | | **改版前每張卡片都有 `0 1px 3px rgba(0,0,0,.06)`，那正是「單調」的來源**——平均分配等於沒有任何一張被強調 |
| emoji 換成 SVG | | emoji 每支手機長得不一樣、不能上色、讀起來像暫代品 |
| 文字自動跟著背景走 | surface / on-surface token | 不用 JS 偵測背景（背景可能是漸層、半透明、被圖片蓋住，取到的值不一定是眼睛看到的）|

**⚠️ 集團給的 logo 檔不能用：**
`assets/logo.svg` 打開是**金色的樹 + 三個事業單位的標誌**（深藍盾牌 / YY Sports 紅字 / pci 藍球），
不是 PCI 單獨的標記；而且 `<path>` 數量是 0 —— 它只是 **247KB 的 PNG 包在 SVG 外殼裡**，
不能用 CSS 改色，裡面那顆 pci 圓球實際只有 81×82 像素。
所以標誌改用**純文字排版**，正式的單色向量檔拿到之後再換。

## 第 6 階段：上線

**分兩步走，不要一次全廠公告。**

| 步驟 | 對象 | 怎麼觸及 | 前提 |
|---|---|---|---|
| **試辦** | 已匯入名冊的 349 位員工 | 請該部門主管在群組發連結，**先不要貼海報** | 第 5 階段完成 |
| **全廠上線** | 約 11,000 人 | 貼海報、正式公告 | 員工名冊補齊 |

⚠️ **為什麼不能用現在的名冊直接全廠上線：**
已匯入 351 / 11,000 筆＝**覆蓋率 3.2%**。
現在貼海報的話，每 100 個掃 QR Code 的人有 **97 個看到「查無此工號」**。

這個系統是**自願使用**的——沒有人規定員工一定要回報。
撞牆一次的人不會再來第二次，而且你沒辦法對 11,000 人重新公告「現在可以了」。
等名冊補齊，大家已經認定「那個東西是壞的」。

> 名冊本身**技術上隨時可以補**：`CACHE_TTL.EMPLOYEE_MISS` 只有 60 秒，
> 貼上新的一批工號，1 分鐘後那些人就能用，不必改程式或重新部署。
> 名冊本來就是活的（每月有新進與離職），**補增加是常態，不是變通做法**。
> 所以問題從來不是「能不能後補」，是「上線那天的覆蓋率夠不夠」。

**海報是最後才貼的東西——一貼就收不回來了。**

- ⬜ 各餐廳專屬 QR Code（帶 `loc` 參數）
- ⬜ 試辦：349 位員工實際使用並收集回饋
- ⬜ 管理者教育訓練 + 操作手冊
- ⬜ 員工名冊補齊（約 11,000 筆）
- ⬜ 海報張貼、正式公告
